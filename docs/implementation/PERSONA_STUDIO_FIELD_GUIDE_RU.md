# Persona Studio: руководство по полям A13

**Основание:** фактический код `cdef078cf8daec8b1b69a4ea45447140b69a1ff7`, API `0.6.1-customer-outcome-review`. Это описание реализации, не новая функциональность и не утверждение качества AI. Все примеры ниже — учебные, из шаблонов либо специально придуманные; реальные беседы и данные сотрудников не включены.

## 1. Сначала прочитайте: где меняются характер и факты

В кабинете наставника откройте **«Конструктор клиентов»**. Характер хранится в `ClientProfile.persona`; факты — отдельно в сценарии. Новый разговор создаётся из выбранной пары **сценарий библиотеки + профиль характера**. Старые разговоры сохраняют собственные снимки.

**Важное ограничение A13:** `PersonaService.compose_pair()` при начале тренировки заменяет встроенный `profile.scenario.source_scenario` актуальной карточкой из библиотеки `scenario`. Поэтому правка текста факта, имени клиента, начала разговора, языка или допустимых исходов внутри Persona Studio сохраняет встроенное досье профиля, **но не обновляет библиотечный сценарий**. Новая тренировка использует библиотечную карточку, а не отредактированные здесь копии её фактов.

Практический порядок:

1. Менять характер — в «Конструкторе клиентов».
2. Менять факты учебного случая — в разделе **«Сценарии»**, сохранив новую редакцию библиотечной карточки.
3. В карточке сценария разрешить нужные профили; в конструкторе поставить «Доступен сотрудникам».
4. Начать новую тренировку с явно выбранной парой и проверить показанные версии.

Назначения профилей хранятся отдельно (`scenario_personas`). Одного флажка доступности недостаточно, если профиль не назначен выбранному сценарию. Если назначений ещё нет, код предлагает два исходных профиля: `decisive_oven` и `indecisive_oven`.

### Что именно видит Simple Actor

Python передаёт: ID клиентского профиля, имя клиента из сценария, Base Persona **без approval**, исходную ситуацию, язык тренировки, разрешённые факты `{id, label, value, status}`, `open_questions`, все модификаторы, историю и текущую реплику сотрудника. История ограничена последними 24 сообщениями; при объёме JSON более 40 000 символов старые сообщения убираются дальше. Начальная ситуация и разрешённое досье передаются снова на каждом ходе.

Карточка компании, список её услуг, критерии оценки, авторские условия раскрытия, `required`, `material`, номера учебных этапов и допустимые исходы **не передаются как внутренние инструкции Actor**. Компания доступна сотруднику и наставнику; произнесённые сотрудником условия попадают к Actor только как реплики, а не как автоматически проверенные факты клиента.

Смысл таблиц ниже:

- **Actor** — значение действительно входит в модельный контекст при сборке новой сессии.
- **Python** — хранение, валидация, выбор, проверка или отчёт; само значение не передаётся модели.
- **Встроенное досье** — редактируемая копия внутри профиля; для запуска действует оговорка о библиотеке выше.

## 2. Общие поля профиля и версии

| Поле интерфейса / JSON | Назначение, тип и допустимые значения | Кто использует, что меняет | Корректный пример |
|---|---|---|---|
| **ID профиля** / `id` | Уникальный строковый ключ. Только `a-z`, `0-9`, `_`, `-`; первая позиция — буква или цифра; 1–80 символов. У существующего профиля поле заблокировано; PUT также запрещает смену ID. | Python: ключ SQLite, назначения, версии. Actor: этот ID становится `customer_id` и должен вернуться неизменным. Не определяет характер или технические факты по названию. | `decisive_oven`, для копии `client_practical_01` |
| **Название** / `persona.name` | Название характера для библиотеки, строка 1–240 символов. Это **не** имя человека в разговоре. | Actor получает в persona; Python показывает в выборе и снимке. Поведенческое обозначение. | «Решительный клиент»; имя «Алексей Бергер» задаётся отдельно в сценарии |
| **Доступен сотрудникам для новой тренировки** / `available` | Boolean, флажок. | Только Python фильтрует доступные профили с учётом назначения сценарию. Не означает утверждение качества. Старые сессии не отключает. | Включить для подготовленного тестового профиля |
| **Профиль v…** / `version` | Целое ≥1, общий номер редакции. При успешном сохранении существующего профиля увеличивается на 1, даже если содержимое не поменялось. Не вводится вручную в форме. | Python: архив и обнаружение конфликта версий. В dossier отдельное поле общей версии не передаётся. | Был v2 → после сохранения v3 |
| **Личность v…** / `persona.version` | Целое ≥1. Увеличивается, когда изменилась хотя бы одна часть persona, кроме самой её версии. | Actor получает номер внутри persona; Python фиксирует в снимке. | Изменили стиль речи: Persona v2 → v3 |
| **Ситуация v…** / `scenario.version` | Целое ≥1 у встроенного блока ProfileScenario. При сохранении растёт при изменении его содержимого. | Python. При создании пары для тренировки заменяется на **revision выбранного библиотечного сценария**. Не путать эти два места. | Профиль v3 + Persona v2 + библиотечный Scenario v4 |
| **Технический черновик / Авторский текст утверждён владельцем** / `persona.approval` | `technical_draft` или `owner_approved`. В текущей форме это подпись, отдельного переключателя approval нет. Поле можно передать при JSON-импорте, затем сохранить. | Python/метаданные; из persona перед отправкой Actor исключается. Не блокирует доступ и не удостоверяет качество. | `technical_draft` до содержательной приёмки |

**«Черновик» и «Доступен» независимы.** Например, решительный v2 — технический черновик, доступный владельцу/сотрудникам для испытаний. `owner_approved` не ставится автоматически после тестов или сохранения. `available=false` не стирает профиль или историю.

У Base Persona есть собственный `persona.id`, у встроенного сценария — `scenario.id`, у библиотечного источника — `source_scenario.id`. Их не следует вручную подменять одним значением. При создании/дублировании UI генерирует ID и связывает `scenario.persona_ids` с новой persona. При сохранении **нового** профиля редактируемый «ID профиля» также задаёт `persona.id`; для существующего профиля переименование не поддерживается.

## 3. Постоянная личность: все поведенческие поля

Эти поля передаются Actor в объекте persona. Они задают **стиль и выбор реакции**, а не утверждённые факты о печи, бюджете, адресе или компании. Индивидуального условия раскрытия для них нет: они присутствуют в каждом dossier. Изменение применяется к новым сессиям после сохранения, не к текущим разговорам.

| Поле интерфейса / ключ | Тип / допустимое значение | Назначение и пример |
|---|---|---|
| **Психологический тип** / `psychological_type` | UI: `decisive`, `indecisive`, `cautious`, `urgent`, `skeptical`, `analytical`, `undecided`, `custom`. Backend допускает обычную строку 1–240 символов. | Метка типа для Actor и сортировки библиотеки. Смена метки **не загружает готовые настройки** остальных полей. Пример: `decisive` плюс самостоятельно заполненный практичный характер. |
| **Характер** / `character` | Строка 1–240 | Основная манера. «Прямой и спокойный; ценит практический результат, не экзаменует продавца». |
| **Стиль речи** / `speech_style` | Строка 1–240 | Форма ответа. «Кратко и естественно, без обязательного перечня требований». |
| **Отношение к продавцу** / `stranger_attitude` | Строка 1–240 | Начальное отношение к незнакомому сотруднику. «Нейтрален; доверие повышается после понятного объяснения». |
| **Поведение при сомнениях** / `doubt_behavior` | Строка 1–240 | Как уточняет существенное. «Уточняет, что входит в диагностику, если это ещё не объяснили». |
| **Манера задавать вопросы** / `question_style` | Строка 1–240 | Тип уточнений, без жёсткого сценария каждой реплики. «Обычно один актуальный вопрос; несколько — когда действительно нужны». |
| **Принятие решений** / `decision_style` | Строка 1–240 | Как двигается к следующему шагу. «После ясного объяснения может условно согласиться обсуждать диагностику, не заказывая ремонт». |
| **Реакция на давление** / `pressure_reaction` | Строка 1–240 | Реакция на навязывание. «Спокойно обозначает сомнение; не принимает обязательство под давлением». |
| **Реакция на повторные вопросы** / `repeat_question_reaction` | Строка 1–240 | Поведение при повторениях. «Кратко напоминает уже сказанное; не начинает объяснение заново без причины». Это инструкция стиля, не отдельная память или детектор повторов. |
| **Дополнительные поведенческие указания** / `additional_behavior` | Строка 0–2000 | Дополнение поведения. «Не повторяй достаточно отвеченный вопрос о документах; переходи к следующему существенному условию». Не размещать здесь скрытые факты, цены, адреса и системные инструкции. |
| **Типичные выражения, по одному в строке** / `typical_expressions` | До 12 строк, каждая 1–240 символов; пустые строки убираются UI | Примеры стиля, не обязательный дословный ответ. «Понятно. Какой следующий шаг?» |

**Особенность валидации:** большинство textarea визуально допускают до 2000 символов, но backend для обычных полей persona ограничивает длину **240**. Длинное значение вызовет ошибку сохранения; для развёрнутого дополнения используйте `additional_behavior`.

Редактируемое поведение не отменяет правила идентичности, фактической достоверности, защиты внутренних инструкций и отсутствия обязывающего заказа. Оно не даёт модели права продвигать учебные статусы.

## 4. Учебная ситуация и досье

Ниже — поля **встроенной копии**. Сохранение в Persona Studio не вызывает `store.save_scenario()`. Для новой тренировки библиотечные значения имеют приоритет.

| Поле | Тип / допустимые значения | Назначение, Actor/Python, пример |
|---|---|---|
| **Взять основу из библиотеки** / `source-case` | Выбор существующего сценария | Сам выбор ещё ничего не копирует. Python/UI-выбор источника. Пример: «Печь снова сломалась · v3». |
| **Применить выбранную основу** | Кнопка | В черновик копируется библиотечный source_scenario, условия всех его фактов ставятся `available`, списки групп фактов очищаются. Это ещё не сохранение. **Открытые темы и модификаторы эта кнопка не очищает** — проверьте их вручную, чтобы не перенести неподходящие обстоятельства. |
| **Название ситуации** / `source_scenario.title` | Строка 1–240 | Название для каталога/отчёта, не прямое поле dossier. «Печь снова сломалась». Новая сессия использует название библиотеки. |
| **Имя клиента** / `source_scenario.customer_name` | Строка 1–240 | Actor получает как customer_name; локальная проверка сверяет заявленное имя. «Алексей Бергер» — учебное имя. Не равно persona.name. |
| **Открытое описание для сотрудника** / `public_brief` | Строка 1–3000 | Python выдаёт сотруднику описание учебного случая; напрямую в dossier не входит. Не помещать сюда закрытые факты. «Клиент сообщает о повторной поломке; уточните оборудование». |
| **Первая реплика клиента** / `opening` | В Scenario строка 1–2000 | Становится первым сохранённым сообщением. В этой форме также копируется в `initial_situation`, у которого предел **240**, поэтому практически ограничьте ввод 240 символами. «Здравствуйте. У меня снова сломалась печь». |
| **Язык** / `language` | Только `ru` / `de` | Actor получает язык **тренировки из библиотеки**, он не связан с языком интерфейса DE/EN/RU. Пример: интерфейс ru, сценарий de. Смена UI-языка не переводит реплики. |
| **Допустимые итоги** / `allowed_outcomes` | Непустой список уникальных ID: `no_fit` либо существующие ID услуг компании; максимум 21 | Python валидирует совместимость карточек/наследуемый учебный контракт. В Actor не передаётся. Пример: `diagnosis`. В A13 ручной коммерческий исход выбирается отдельно; этот список не превращает диагностику в заказ ремонта. |

При применении новой библиотеки или редактировании фактов сначала проверьте досье в предпросмотре. Предпросмотр показывает черновой JSON, **не окончательную сборку будущей пары**.

## 5. Факты: каждая строка и условие раскрытия

В Scenario требуется 2–20 фактов. ID уникальны; у каждого из этапов `needs` и `capabilities` должен быть хотя бы один обязательный применимый факт. Пустое значение обычного Fact не допускается: неизвестность описывается явно через status и корректный текст.

| Поле интерфейса / ключ | Тип / допустимые значения | Кто получает, влияние, пример |
|---|---|---|
| **ID** / `facts[].id` | Строка по правилу ID: 1–80, `[a-z0-9][a-z0-9_-]*` | Actor получает ID разрешённого факта; Python использует для связей, условий и отдельных проверок. Это ключ, не человекочитаемая подпись и не числовой вес. Пример `priority`. Переименование меняет ключ раскрытия; удалённые ссылки из списков групп удаляются, но не заменяются новым ID автоматически. |
| **Название** / `label` | Строка 1–240 | Actor получает вместе с фактом; Python показывает наставнику. Семантически объясняет тему. Пример «Допустимые сроки». |
| **Этап** / `stage` | `needs` или `capabilities` | Python: группировка фактов в разборе, валидация, legacy-логика. В Simple Actor stage **не включён** в authorized_facts. Не открывает факт автоматически. Пример timing → capabilities. |
| **Состояние знания** / `status` | Пять вариантов из таблицы ниже | Actor получает статус вместе со значением, **если раскрытие разрешило факт**. Python валидирует комбинации. Пример budget → undecided. |
| **Раскрытие** / `disclosure_conditions[id]` | `available`, `after_needs`, `after_capabilities`, `owner_only` | Python фильтрует authorized_facts до вызова; сама карта условий Actor не передаётся. Подробности ниже. |
| **Утверждённое содержание** / `value` | Строка 1–2000 | Разрешённая автором фактическая информация либо явно описанная неизвестность. Actor получает только вместе с разрешённым фактом. «Желательно разобраться в течение недели». Не вводить предположение от имени клиента как известный факт. |
| **Критерий разбора этапа** / `required` | Boolean | Только Python. В Simple Actor не выдаёт балл, не определяет семантически полноту ответа и не продвигает этап. Наставнику остаётся ручная проверка. При not_applicable UI снимает required; включение required также ставит material=true. |
| **Существенный факт** / `material` | Boolean | Только Python/legacy-правила. Не приоритет внимания модели. Обязательный факт не может быть несущественным. Пример equipment: true; необязательный поясняющий симптом: false. |

Статусы обычного факта:

| Значение | Смысл | Пример корректного содержания |
|---|---|---|
| `known` | Клиент знает утверждённое обстоятельство | «Это бытовая электрическая печь на домашней кухне». |
| `does_not_know` | Автор утвердил, что клиент этого не знает | «Причину неисправности я не знаю; специалист её ещё не определил». |
| `undecided` | Решение ещё не принято | «Бюджет пока не определён; сначала нужна оценка стоимости». |
| `refuses_to_disclose` | Клиент не раскрывает сведения | «Точную сумму не называю; готов обсудить порядок оценки». Статус не является запретом отправки value модели: важен также disclosure. |
| `not_applicable` | Вопрос не относится к ситуации | «Согласование с другим лицом не требуется». required должен быть false. |

**Отсутствие данных автора — не `does_not_know`.** Для него есть отдельный блок open_questions со статусом `author_missing`. «Автор не сообщил дату обслуживания» не означает «клиент забыл эту дату» и не разрешает придумать дату.

### Как Python раскрывает факты в Simple Actor

| Выбор «Раскрытие» | Фактическое условие в dossier() | Что это означает в A13 |
|---|---|---|
| **Разрешён клиенту** / `available` | Всегда включается в authorized_facts | Модель видит факт на каждом ходе, но получает инструкцию отвечать по вопросу, не выгружать всё досье сразу. Это не автоматическая публикация сотруднику. |
| **После подтверждения потребностей** / `after_needs` | `session.state.needs_confirmed == true` | Это флаг Python, **не** наличие слова «потребности», нужного вопроса или ответа в истории. |
| **После подтверждения возможностей** / `after_capabilities` | `session.state.capabilities_confirmed == true` | Это флаг Python, а не признание компетентности в реплике сотрудника. |
| **Только наставнику** / `owner_only` | Не включается в authorized_facts | Не поступает через этот список в Actor. Не дублируйте закрытый текст в persona, opening, open_questions, modifiers или истории: эти каналы имеют собственные правила. |

**Практическое ограничение:** новые сессии A13 используют Simple Actor. Он не меняет needs_confirmed/capabilities_confirmed во время разговора; новая независимая оценка наставника после завершения тоже не меняет разговорное state. Поэтому `after_needs` и `after_capabilities` в обычной новой активной сессии остаются закрытыми. Это не готовый механизм смыслового раскрытия по вопросам. Для теста, где клиент должен иметь возможность отвечать на обычный вопрос о сроках/бюджете, используйте `available`; более тонкую политику нужно отдельно согласовать, не предполагая её существования.

При сборке **другого** библиотечного сценария, чей ID отличается от встроенного источника профиля, compose_pair устанавливает все факты available, очищает группы/open_questions и сбрасывает modifiers к author_missing. При совпадении ID сохраняет подходящие условия по ID факта; новый факт библиотеки без прежнего условия получает available. Содержимое фактов в обоих случаях берётся из библиотеки.

## 6. Особенно важные ID: priority, reason, budget, timing

Это значения **колонки ID у обычных фактов**, а не четыре самостоятельных типа полей или скрытые настройки интенсивности Actor. В Simple Actor нет отдельной числовой настройки priority и нет функции, которая по самому имени budget рассчитывает цену.

| ID | Фактический смысл в исходных сценариях | Actor / Python и корректное заполнение |
|---|---|---|
| `priority` | Что существенно для **клиента при выборе решения**, не «приоритет инструкции» и не ранг вопроса | Обычный разрешённый факт. В oven_uncertain v3: «Важно понять причину повторной поломки и получить понятную оценку вариантов», known, needs. В других шаблонах — подходящие размеры/управление либо специализация исполнителя. Не помещать сюда «требуй документы в каждом ответе»: это поведенческая инструкция не по назначению. |
| `reason` | Причина обращения/выбора исполнителя, в зависимости от label и текста данного сценария | Обычный разрешённый факт. В oven_uncertain v3 прежний мастер недоступен две недели; в oven_replacement нужна помощь с подбором/установкой; в oven_no_fit прежняя фирма перестала обслуживать город. **Это не причина поломки.** Для неизвестного диагноза в шаблоне отдельно есть `cause`. |
| `budget` | Собственный бюджет клиента либо авторское состояние знания/решения о расходах | Обычный разрешённый факт. В uncertain — undecided; replacement — known с общим пределом 2000 евро; no_fit — does_not_know, стоимость ремонта неизвестна. Бюджет не равен сумме, объявленной продавцом, и не является согласием на оплату. Не копируйте сюда 90 евро из карточки компании, если это не факт о клиенте. |
| `timing` | Допустимый **будущий** срок решения/установки/ожидания | Обычный разрешённый факт. В uncertain: «Желательно разобраться в течение недели», known, capabilities. Это **не дата последнего техосмотра**, не периодичность обслуживания и не подтверждение записи на конкретный день. |

Для любого из этих ID действует ровно та же disclosure_conditions[id]. Например, `budget + undecided + available` разрешает клиенту сказать, что бюджет ещё не выбран; `budget + after_capabilities` не сработает лишь потому, что сотрудник спросил о цене. `priority + known + owner_only` исключит этот value из authorized_facts, но не из других каналов, если автор сам продублировал его туда.

Имена не следует без необходимости переименовывать. В legacy-модуле планирования есть тематические привязки (например, исключение timing из вопроса о прошлом обслуживании). В Simple Actor priority/reason/budget/timing не вызывают отдельную LLM-цепочку или автопереход; их смысл задают label/value/status. При этом **некоторые другие** ID реально проверяются программно: `goal` и `equipment` используются локальной проверкой известных противоречий типа оборудования. Поэтому ID — часть контракта, а не произвольный декоративный заголовок.

Списки `reason_fact_ids`, `observation_fact_ids`, `need_fact_ids`, `financial_fact_ids`, `timing_fact_ids` содержат ссылки на существующие ID. В текущей форме отдельных редакторов этих списков нет: capture удаляет несуществующие ссылки, «Применить основу» очищает списки. Simple Actor dossier эти группы не читает и модели их не передаёт: они не являются механизмом раскрытия и не делают факт обязательным. Модель получает сами разрешённые факты.

## 7. Неизвестные или отсутствующие сведения

Это `scenario.open_questions`: до 30 тем. **Весь блок передаётся Actor**, индивидуальных условий раскрытия здесь нет. Он пригоден для честного описания неизвестности, а не для хранения информации «только наставнику».

| Поле интерфейса | Тип / значения | Назначение и пример |
|---|---|---|
| **Название темы** / `label` | Строка 0–240 | Actor получает пояснение темы. «Дата последнего технического осмотра». |
| **Тема / ID** / ключ словаря | По правилу Identifier, 1–80 | Actor получает ключ; Python проверяет формат. Пример `last_inspection`. Пустой ключ UI не сохраняет; одинаковые ключи при сборке словаря могут перезаписать предыдущую строку — используйте уникальные. |
| **Состояние** / `status` | `known`, `customer_unknown`, `author_missing`, `undecided`, `refuses_to_disclose`, `not_applicable` | Это другой enum, чем у обычных facts: **customer_unknown**, а не does_not_know. Пример author_missing, если автор не задал дату. |
| **Разрешённое пояснение, пусто для отсутствующих данных** / `value` | Строка 0–3000; для known непустая, для author_missing обязательно пустая | Для author_missing оставить `""`. Для customer_unknown: «Клиент не знает дату последнего осмотра». Не писать известную дату в пояснении неизвестного значения. |

Смысл `undecided` — решение не принято; `refuses_to_disclose` — отказ сообщить; `not_applicable` — неприменимо. Пустое значение с другим статусом в некоторых случаях пройдёт структурную проверку, но без понятного label авторское досье будет неоднозначно. Backend не превращает незаполненное поле в авторский факт автоматически.

При применении новой основы UI не удаляет этот блок. При запуске пары он сохраняется только при совпадении ID встроенного источника с выбранным сценарием. Проверяйте итоговый выбор, не предполагая, что тема автоматически относится ко всем трём сценариям.

## 8. Изменяемые условия — Session Modifiers

В раскрываемом разделе формы пять полей. Каждое редактируется парой **Состояние + Проверенное значение**, с теми же шестью статусами ProfileField, что у open_questions. Все пары передаются Actor. Поле status задаёт, что автор считает установленным; автоматической проверки внешней правды за словом «Проверенное» нет.

| Поле / ключ | Что меняет | Пример корректной пары |
|---|---|---|
| **Настроение** / `mood` | Поведение в этой ситуации | known + «Спокоен, готов выслушать ясное объяснение». |
| **Срочность** / `urgency` | Дополнительное условие/поведение; не должно противоречить timing | known + «Готов обсуждать варианты в пределах указанной недели». Не придумывать новую крайнюю дату. |
| **Предыдущие переговоры** / `previous_conversation` | Проверенный автором предыдущий опыт, **не** автоматическая межсессионная память | author_missing + пустое значение, если предыдущий разговор не задан. |
| **Сравниваемые предложения** / `compared_offers` | Дополнительные факты об альтернативах | author_missing + пустое значение, если настоящего утверждённого предложения нет. Не выдумывать конкурента и цену. |
| **Текущее доверие** / `trust_level` | Авторская начальная установка, не вычисляемый рейтинг | known + «Нейтрален, готов рассмотреть практическое объяснение». Это строка, не шкала 0–100. |

Каждое value 0–3000, label 0–240; known требует непустое value. UI для author_missing очищает value перед сохранением. У open_questions такое автоматическое очищение не выполнено — там оставьте поле пустым самостоятельно.

Схема также содержит `verified_experience` — объект того же типа. В визуальном редакторе A13 для него нет отдельного поля; он может присутствовать в JSON-импорте. Он тоже передаётся Actor. Python дополнительно включает value модификаторов со статусом known в набор свидетельств для узких локальных проверок, поэтому не храните в них неподтверждённые суммы/биографию.

При изменении содержимого modifiers их собственная version увеличивается. При создании пары с другим встроенным source ID модификаторы сбрасываются к значениям по умолчанию — это не глобальные настройки всех ситуаций клиента.

## 9. Кнопки, сохранение и ограничения версий

| Действие | Фактический результат |
|---|---|
| **Новый клиент** | Клонирует выбранный либо первый профиль как основу, генерирует новый ID, ставит версии 1 и available=false. Это **не пустой бланк**: внимательно проверьте унаследованные факты, approval, дополнительные условия и характер. |
| **Дублировать** | Аналогично создаёт новую сущность с новым ID и названием-копией, а не меняет существующий профиль. approval явно не сбрасывается; проверьте его в предпросмотре/JSON. |
| **Предпросмотр** | Показывает текущий собранный JSON; не сохраняет, не вызывает OpenAI и не симулирует compose_pair для каждого библиотечного сценария. |
| **Экспорт JSON** | Скачивает **сохранённый** профиль из загруженной библиотеки; несохранённый черновик в экспорт не попадает. Новый ещё не сохранённый профиль экспортировать этой кнопкой нельзя. JSON может содержать закрытые авторские факты: хранить его соответственно. |
| **Импорт JSON** | До 200 000 байт на уровне UI. Проверяет структуру Pydantic и допустимые исходы, открывает черновик. При совпадении ID подставляет текущую общую version для последующего сохранения. **Не сохраняет автоматически**. Не является переносом истории/пользователей. |
| **Сохранить новую версию** | POST для нового / PUT для существующего; права наставника обязательны. Общий профиль сохраняется в SQLite documents/client_profile, архивная редакция — client_profile_version. Сценарий библиотеки этим запросом не обновляется. |
| **Добавить/удалить факт или тему** | Меняет черновик; постоянный результат появляется только после успешного сохранения. У каждого факта должен остаться уникальный ID и условие раскрытия. |

При сохранении существующего профиля:

1. Backend сверяет присланную общую version; при конфликте возвращает ошибку, а не молча перезаписывает новую чужую редакцию.
2. Общая `ClientProfile.version` увеличивается всегда.
3. `persona.version`, `scenario.version`, `modifiers.version` увеличиваются отдельно, только при изменении соответствующего блока без учёта его version.
4. При изменении встроенного `source_scenario` его `revision` также увеличивается, **но только во встроенной копии**, не в библиотеке.
5. Уже созданные тренировки, их сообщения, имя клиента, выбранный характер, факты, компания и результаты не меняются. Продолжение старой тренировки использует прежний snapshot.
6. Новая тренировка получает текущую Persona и актуальную библиотечную Scenario. Изменение библиотеки может поменять Scenario revision новой сессии даже без смены общего номера профиля. Для воспроизводимости нужны все выбранные версии **и полный session snapshot**.

При создании новой сущности значения внутренних версий из импортированного JSON не обязательно перенумеровываются автоматически: UI «Новый/Дублировать» ставит 1, но произвольный импорт может нести иные номера. Не используйте вручную завышенную version как отметку качества.

### Служебные поля JSON, у которых нет отдельного поля формы

- `schema_version=1` — версия формата ClientProfile, а не редакция персонажа. Python проверяет её, Actor отдельно не получает.
- `source_scenario.company_id` — ссылка Python на компанию, не источник права модели обещать её услуги.
- `source_scenario.question_hints` — до 30 учебных подсказок строками до 500 символов; не входят в dossier Simple Actor.
- `facts[].keywords` — до 24 строк по 1–100 символов; UI сохраняет прежний список, у добавленного факта он пуст. В Simple Actor ключевые слова не отправляются и не используются как обязательный классификатор; относятся к прежней логике.
- `scenario.persona_ids` — непустой список ID разрешённых persona, проверяется Python. Не является библиотечным назначением сценария сотрудникам: это отдельная запись scenario_personas.
- `critical_contradictions` — список служебных флагов. В JSON допустимы equipment_is_customer_owned, industrial_gas_not_domestic_electric, no_confirmed_repair_price, no_confirmed_booking. При создании пары Python собирает собственный фиксированный список; это не свободный текст поведения. Текущая Simple Actor-проверка использует флаг владельца оборудования, а часть остальных ограничений проверяет безусловно по коду/утверждённому оборудованию. Сам список не передаётся Actor, универсальной проверки всех фактов по этим названиям нет.

## 10. Что не следует считать реализованным

- Нет числового регулятора «решительность» или автоматической подстановки поведения по psychological_type.
- Нет автоматического раскрытия «после нужного вопроса» и автоматического подтверждения учебных этапов Simple Actor.
- Нет полноценной синхронизации встроенного досье Studio с библиотекой сценариев.
- Нет отдельной текущей настройки режима technical_knowledge/company_procedure или уровня сложности. `simple_actor` — способ работы AI, а не вид учебной компетенции.
- Нет автоматического экзаменатора: три этапа, коммерческий результат и соответствие компании в A13 оценивает наставник.
- Нет строгой универсальной семантической проверки правдивости каждой реплики. Стиль и факты не должны смешиваться, но один промпт не доказывает отсутствие будущих выдумок.

Эти ограничения зафиксированы отдельно в [сопоставлении архитектуры с A13](../decisions/2026-11-07_A13_IMPLEMENTATION_ALIGNMENT_RU.md). Они намеренно **не исправлялись** в документационной миссии A13.1.
