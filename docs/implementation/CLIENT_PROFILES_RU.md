# A09: клиенты и ручная приёмка simple_actor

Запустите START_TRAINER.command. Адрес прежний: http://127.0.0.1:8100.
На странице «Тренировка» выберите **OpenAI · simple_actor**, затем клиента.
Доступны пять технических черновиков: Cautious, Urgent, Skeptical, Undecided,
Analytical. Все играют Дениса Брауна в существующей ситуации промышленной
газовой печи. Манеры не утверждены владельцем. Версии видны в беседе и экспорте.
Старый многозвенный режим сохранён под названием **OpenAI · legacy**; сохранённые
старые беседы сохраняют исходный режим и никогда не переключаются автоматически.

## Что меняется в разговоре

Один вызов Responses API генерирует ответ. Python передаёт клиентское досье,
разрешённые факты, действующие модификаторы, последние сообщения и текущий ввод.
Внутренняя карточка компании и rubric не передаются. Заявления продавца остаются
его словами. Нет Director или обязательного LLM-Verifier на каждом ходе;
нет автоматических повторов, шаблонных подстановок или автономных агентов.
Используется прежняя модель сервера, ключ из Keychain, store=false. История берётся
из SQLite, до 24 последних сообщений, сокращается с начала при превышении 40000
символов сериализованной истории. Старый разговор целиком остаётся в SQLite.

Модель не выставляет оценки и не закрывает учебные этапы. Кнопки «Вопрос»,
«Резюме», «Предложение» не навязывают модели тип действия: она читает фактический
текст. Предложение или резюме могут получить обычную естественную реакцию.
Программные проверки блокируют отдельные явные нарушения структуры, идентичности,
роли, сумм, обязательств и критических противоречий. Это **не строгая проверка
всех смыслов**: тонкие выдумки и недостаточную релевантность проверяет владелец.
Отклонённый ответ не сохраняется как сообщение; API-попытка и техническая ошибка
учитываются отдельно. Можно исправить/повторить ввод вручную; скрытых повторов нет.

После беседы нажмите «Завершить и разобрать», сохраните PDF/JSON и при желании
«Отправить наставнику». В рабочем месте наставника откройте разбор, оставьте отзыв.
Дополнительный флажок «Сохранить мою оценку этапов» позволяет явно подтвердить
потребности, затем возможности, затем разрешённый обоснованный итог. Нельзя
подтвердить второй этап без первого или итог без обоих. Это оценка наставника
после беседы, не автоматическая оценка модели. Раннее предложение не засчитывается
успешным. В живом диалоге ступень остаётся неподтверждённой до ручного разбора.
Факты помечены «не оценено автоматически», чтобы отсутствие автоматики не
трактовалось как ошибка ученика. Содержательные наблюдения отделены от system issues.

## Три независимых блока

Схема JSON: `profiles/client-profile.schema.json`; валидируемые модели:
`backend/app/dashboard/client_profiles.py`.

- `persona`: id, version, name, approval; character, speech_style,
  stranger_attitude, doubt_behavior, question_style, decision_style,
  pressure_reaction, typical_expressions. Заполните каждый параметр обычным языком.
  Не добавляйте сюда биографические/финансовые факты или обстоятельства сценария.
  Примеры выражений — ориентир стиля, не обязательные ответы.
- `scenario`: id/version, persona_ids; source_scenario с исходной карточкой,
  initial_situation, ссылки на факты причины/наблюдений/потребности/денег/времени,
  open_questions, disclosure_conditions, critical_contradictions.
  Факты и их статусы находятся в source_scenario.facts, неопределённые решения —
  status=undecided, допустимые исходы — source_scenario.allowed_outcomes.
  Исходная oven_no_fit revision=2 перенесена без изменения единого значения факта.
  Поле даты последнего осмотра явно author_missing; это не утверждение, что клиент
  забыл осмотр. Любое изменение фактов требует новой версии сценария и профиля.
- `modifiers`: независимая version и поля mood, urgency, previous_conversation,
  compared_offers, trust_level, verified_experience. Каждое — объект status/value.
  Эти поля уже читаются и передаются Actor. Добавляйте только проверенный опыт,
  а не выводы из неподтверждённого заявления ученика.

Состояния ProfileField: `known` требует непустое value; `customer_unknown` означает
явно заданное незнание клиента; `author_missing` требует пустое value и означает
отсутствие авторских данных; также `undecided`, `refuses_to_disclose`,
`not_applicable`. В исходных фактах сохраняется прежнее имя `does_not_know`.
Не превращайте author_missing в выдуманное знание, воспоминание или биографию.

Каждому факту задаётся disclosure_conditions: available, after_needs,
after_capabilities, owner_only. Последний не отправляется Actor. В simple_actor
этапы живого разговора автоматически не подтверждаются; отложенные сведения
по этим условиям в такой беседе не откроются. Для обычного разговора о данном
случае все факты установлены available: клиент их знает/не знает согласно статусу,
но не обязан выдавать всё сразу. Новые сценарии, требующие динамического раскрытия
по смыслу вопросов, потребуют отдельного согласованного расширения, а не обхода правил.

## Как редактировать без потери при обновлении

Поставляемые шаблоны: profiles/personas/*.json, profiles/scenarios/*.json,
profiles/clients/*.json. Binding связывает persona_id и scenario_id. Один характер
можно использовать в нескольких сценариях; несколько характеров — в одном.
Схема не ограничена пятью клиентами; 5–10 профилей не требуют нового движка.

Для пользовательской версии не меняйте поставляемый Git-код. Сохраните полный
ClientProfile (с тремя развёрнутыми блоками) в
`runtime/client_profiles/<id>.json`. Папку можно создать в Finder. Полные образцы
доступны локально через `/api/mentor/client-profiles` с заголовком рабочего места
наставника; Codex может помочь выгрузить образец и внести ваши согласованные правки.
При совпадении ID version должна быть больше поставляемой. Для нового клиента
задайте новый id и соответствующую привязку persona_ids. Изменяйте версии блоков
при изменении их содержания. approval=owner_approved означает только ваше
утверждение авторского текста, не доказательство качества модели.

Проверка без API: `.venv/bin/python scripts/validate_client_profiles.py`.
Ошибка схемы должна быть исправлена: некорректный профиль не подменяется молча.
Применение: STOP_TRAINER.command, затем START_TRAINER.command. Новые беседы получают
новый снимок; старые сохраняют прежние профиль/сценарий/модификаторы. JSON-файлы в
runtime исключены из Git и сохраняются обновлением. API-ключ в них не помещайте.
Масштабный редактор профилей в A09 не реализован.

## Обновление и откат

UPDATE_TRAINER.command использует явно закреплённый release, не main/latest.
A09 устанавливается тем же механизмом из локального проверенного Git bundle;
push/merge для этого не нужен. После установки `runtime/last-update.json` хранит
предыдущий SHA и путь резервной копии исходной базы/окружения. Откат:
`.venv/bin/python scripts/local_installation.py update --rollback`.
Он сохраняет новые беседы; старый код может показывать simple_actor некорректно,
поэтому экспортируйте A09-беседы до отката и не продолжайте их в legacy-коде.
A04–A08 и прежние отчёты остаются сохранены. Единственная активная установка и
адрес не меняются.
