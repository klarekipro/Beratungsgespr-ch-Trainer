Режим тренера и лицензии для учебных центров представлены в концепции (стр. 5–7), но их правовые и технические условия ещё предстоит определить. ## 1. Назначение и условия расширения

**ПРЕДЛОЖЕНИЕ:** назначение первой версии — добровольная личная тренировка на вымышленных ситуациях. Система показывает учебный разбор конкретного разговора. Результат не используется для найма, продвижения, увольнения, допуска к профессии или официальной аттестации.

| Уровень | Допустимый режим по предложению A01 | Условие перехода |
|---|---|---|
| Level 1 — WBS MVP | Один владелец на своём компьютере, браузер и backend через loopback; локальная PostgreSQL в Docker. Владелец также создаёт карточки в роли автора-тренера. | Закрытая локальная поверхность, безопасная обработка запросов и фиктивные клиентские данные. |
| Level 2 — личный рабочий продукт | Приглашённые пользователи тренируются самостоятельно; каждый видит только свои сессии. | Аутентификация, серверная авторизация, TLS, проверка договоров/провайдеров, privacy notice, работающие удаление и изоляция пользователей. |
| Level 3 — коммерческое использование | Возможна добровольная передача выбранного результата конкретному тренеру. | Явное отзываемое разрешение на каждую сессию; правовое основание и договорные роли определены; назначение проверено заново. |
| Level 4 — расширения | Голос, собственные кейсы, институциональные функции рассматриваются отдельно. | Новый анализ потоков данных, рисков и классификации до добавления функции. |

Локальный интерфейс не делает обработку полностью локальной: текст, отправленный через LLM API, покидает компьютер. Показ экрана на защите можно организовать с владельцем за клавиатурой; предоставление другим людям удалённого доступа уже требует условий Level 2.

**НОРМА:** Annex III 3(b) AI Act охватывает предусмотренное назначением оценивание результатов обучения в образовательных и профессиональных учебных учреждениях; Annex III 4 касается ряда кадровых решений и оценки работы/поведения работников. Условия Article 6 требуют отдельного анализа. Само название «учебный тренажёр» не устанавливает категорию риска. [S8]

**ПРОВЕРИТЬ:** до институционального оценивания, автоматического управления обучением или кадровых сценариев подготовить письменную классификацию конкретной версии и её назначения. Запрет работодателю оценивать сотрудников не решает автоматически вопрос учебного центра. Не выдавать текущему PoC заключение «не high-risk» без этой проверки.

## 2. Данные и границы передачи

**НОРМА:** сведения об идентифицируемом ученике могут быть персональными данными, включая связанные с ним результаты. Замена имени идентификатором не гарантирует анонимность. Необходимы ограничение цели, минимизация и ограничение хранения. [S2]

**ПРЕДЛОЖЕНИЕ:** использовать следующую карту данных.

| Данные | Назначение | Где доступны | Что ограничить |
|---|---|---|---|
| Публичная часть вымышленной карточки | Задать исходную ситуацию | UI, backend, Actor | Никаких реальных клиентских контактов. |
| Скрытые факты и правила раскрытия | Управлять сценарием | Scenario/Policy на сервере; Actor получает разрешённую часть | В HTML, JSON загрузки страницы и браузерный bundle скрытые факты не попадают до предусмотренного разбора. |
| Реплики и связанные события | Провести тренировку и объяснить её результат | Ученик, backend, минимально необходимая часть в LLM | Произвольный ввод может содержать реальные персональные данные. |
| Итоговый разбор | Обратная связь ученику | Владелец сессии; позже указанный получатель по разрешению | Связь с человеком сохраняет чувствительность результата. |
| Личный прогресс | Сравнить собственные попытки | Владелец профиля | Отдельный ограниченный срок; без рейтинга сотрудников. |
| Учётная запись и доступ | Идентифицировать пользователя Level 2+ | Identity/API/БД | Минимум полей; не отправлять email или auth-данные в LLM. |
| Технические события и usage | Разбирать сбои и контролировать расходы | Оператор | Без текста диалога, скрытых фактов, токенов доступа и полных prompts. |
| Резервные копии | Восстановить сервис | Ограниченный операторский доступ | Шифрование, срок истечения, проверка удаления после восстановления. |

Поток основной операции: браузер → FastAPI → Session/Policy → LLM Gateway → провайдер; проверенный результат → PostgreSQL → браузер. Gateway получает только подготовленный для данной роли контекст. Director не получает полную скрытую карточку; Actor — неразрешённые факты. Это одновременно контроль сценария и сокращение передаваемых данных, но не универсальная гарантия конфиденциальности модели.

MVP использует утверждённые вымышленные карточки. Загрузка записей настоящих переговоров, документов клиентов, аудио и медицинских историй относится к отдельному будущему scope. Ввод нельзя считать безопасным только потому, что UI просит не вставлять персональные данные.

## 3. Роли и доступ к результатам

**ПРЕДЛОЖЕНИЕ:** применять серверную проверку владельца ресурса на каждом чтении и изменении. Непредсказуемый UUID, скрытая кнопка и фильтр на frontend не заменяют авторизацию.

| Роль | Свои тренировки | Карточки сценариев | Чужие диалоги и разборы |
|---|---|---|---|
| Ученик | Создание, чтение, завершение, экспорт и удаление своих данных | Публичная карточка; разбор после завершения | Доступ отсутствует. |
| Автор-тренер | Как ученик, если тренируется сам | Создание и редактирование разрешённых ему карточек | Право авторства не даёт доступа. |
| Приглашённый тренер, Level 3 | Только свои и явно переданные результаты | В пределах назначения | Только конкретная сессия, конкретный объём и действующий срок разрешения. |
| Оператор | Настройка и техническая диагностика | Управление доступом по назначению | В обычном интерфейсе доступа к содержимому нет. Исключительный технический доступ требует основания, минимального объёма и журнала. |

В Level 1 владелец и автор-тренер — один человек. Это упрощение не превращается в глобальную роль, читающую все данные при добавлении пользователей. Для Level 2 сохраняется изоляция личных результатов, даже если несколько пользователей получили приглашения от одного тренера.

Будущий `sharing_grant` содержит владельца, получателя, `session_id`, разрешённый объём (`feedback` или отдельно согласованный `transcript`), время создания, истечения и отзыва. По умолчанию передача выключена. Отзыв закрывает дальнейший доступ; уже скачанную копию нельзя технически отозвать с устройства получателя. Это ограничение показывается до передачи. Публичная ссылка без аутентификации не предлагается.

Уровень прав на сценарий также разделяется: право редактировать карточку не должно позволять переписать версию, использованную в завершённой тренировке. Идентификаторы сценария и версии сохраняются для объяснимости оценки; они не дают доступа к чужой сессии.

## 4. Правовые основания и договорные роли

**НОРМА:** основание обработки определяется по цели. Договорная необходимость должна быть реальной; согласие — свободным, конкретным, информированным и отзываемым. В трудовых отношениях свобода согласия может отсутствовать. Для специальных категорий данных нужны дополнительные условия Article 9. [S1]

**ПРЕДЛОЖЕНИЕ, подлежит проверке до внешних пользователей:**

| Цель | Кандидат основания и вопрос для проверки | Архитектурное следствие |
|---|---|---|
| Предоставить заказанную личную тренировку | Article 6(1)(b), если обработка объективно необходима для действительного договора | Минимально необходимая сессия; лишние поля не становятся необходимыми через текст условий. |
| Сохранить историю и личный прогресс | Определить, входит ли это в запрошенную услугу; для отдельной добровольной цели рассмотреть подходящее основание | Отдельная настройка, ограниченный срок и удаление. |
| Обеспечить безопасность сервиса | Возможный Article 6(1)(f) после оценки необходимости и баланса интересов | Технические метаданные без содержимого диалогов. |
| Передать результат выбранному тренеру | Проверить основание для конкретной договорной ситуации; интерфейсное разрешение его не заменяет | Отзываемый доступ к одной сессии; получатель и объём видны ученику. |
| Исследование, маркетинг, обучение моделей | За пределами MVP; отдельная цель и самостоятельная проверка | Никакого автоматического повторного использования тренировок. |

**НОРМА:** controller определяет цели и средства; processor обрабатывает данные по его поручению. Для отношения controller–processor нужен договор по Article 28, включая необходимые условия о subprocessors. Международная передача требует соблюдения Chapter V дополнительно к основанию обработки; применимая adequacy decision или соответствующие safeguards проверяются для фактического маршрута. [S3, S4]

**ПРОВЕРИТЬ:** реестр поставщиков должен фиксировать юридическое лицо, роль, назначение, категории данных, регион хранения и обработки, subprocessors, DPA/AVV, механизм передачи и контакт для удаления. Это относится к LLM, hosting, backups и monitoring. Для клиентов-организаций роли определяются фактическими договорённостями; нельзя заранее объявить Klare KI только processor во всех вариантах.

## 5. Хранение и удаление

### 5.1. Предлагаемые значения по умолчанию

**ПРЕДЛОЖЕНИЕ ДЛЯ СОГЛАСОВАНИЯ:** сроки применяются к данным приложения; условия хранения внешнего провайдера учитываются отдельно. Срок рассчитывается автоматически, а не откладывается до ручной уборки.

| Класс | Предлагаемый предел | Событие и действие |
|---|---|---|
| Незавершённая тренировка | 24 часа неактивности | Удалить временное содержимое, если пользователь не сохранил тренировку в допустимую историю. |
| Сохранённые личные диалоги, события и подробный feedback | 30 дней после завершения | Ежедневная задача очищает содержимое. Пользователь может удалить раньше. |
| Производный личный прогресс | 90 дней от соответствующей тренировки при включённой функции | Только минимальные outcome counts, версии и repeat-признак, без цитат/текста. Явное удаление сессии пользователем/аккаунта исключает вклад; автоматическое истечение подробного содержимого на 30-й день не обязано удалять отдельно согласованный минимальный прогресс. |
| Операционные логи без содержимого | 14 дней | Автоматическая очистка; минимальные технические идентификаторы. |
| Временный экспорт на сервере | До 24 часов | Удалить созданный файл и истечь ссылку; предпочтительно выдавать напрямую без постоянной серверной копии. |
| Зашифрованные резервные копии | 30 дней от создания | Автоматическое истечение; исключение удалённых данных при восстановлении. |
| Учётная запись Level 2+ | Пока нужна для действующей услуги | При удалении аккаунта запустить каскадную очистку; отдельно обработать обоснованные исключения. |

Технический audit хранит только необходимое: тип события, время, request ID, результат и минимальный внутренний идентификатор там, где он нужен. Он не является вечным хранилищем реплик или оценок. По окончании срока идентификатор удаляется либо проводится проверяемая анонимизация; простое хеширование не объявляется автоматически анонимизацией.

Раздельные 30/90 дней — предложение двух целей хранения: подробный разбор и минимальная личная динамика. После удаления подробностей прежний transcript/полный разбор восстановить нельзя. Если владелец не принимает отдельное хранение прогресса, единый срок 30 дней применяется ко всем данным тренировки. Это должно быть понятно в настройках и уведомлении пользователю.

Исторические исследовательские raw-файлы базового PoC уже исключены из Git и имеют отдельный локальный архив по handoff. A01 не переносит их в пользовательскую БД и не меняет их статус. Для будущих evals нужны синтетические примеры или отдельно разрешённые и обработанные материалы.

### 5.2. Процедура удаления

**ПРЕДЛОЖЕНИЕ:** пользовательское удаление немедленно закрывает доступ и отменяет sharing grants. Активные данные очищаются сразу либо надёжной идемпотентной задачей не позднее 24 часов. Это техническая цель приложения, а не установленный законом срок для любого запроса.

1. Проверить владельца и принять один идентификатор операции удаления.
2. Сделать сессию недоступной, отменить передачу, выгрузки и незавершённые операции, которые могли бы сохранить её снова.
3. Удалить сообщения, содержательные события, feedback, временные exports и связанные данные прогресса; пересчитать агрегаты без этой сессии.
4. Очистить cache и диагностические копии, если они всё же были созданы по отдельной процедуре.
5. Сохранить минимальный факт исполнения и необходимые для восстановления маркеры удаления отдельно от удаляемого содержимого.
6. Дать пользователю достоверный результат: выполнено, в обработке либо ограничение с конкретным основанием.

Резервные копии изолированы от обычного чтения и истекают в установленный срок. Журнал удаления содержит минимальные непрозрачные идентификаторы и переживает окно восстановления: например, 35 дней при 30-дневных backups. При восстановлении сначала применяются удаления и retention, затем открывается доступ; откат БД не должен возвращать удалённые сессии. Такой журнал тоже имеет срок, ограничения доступа и процедуру очистки.

**НОРМА:** право на удаление имеет условия и исключения; общий срок ответа на запрос субъекта — один месяц с предусмотренной процедурой продления. Article 20 о переносимости имеет более узкие условия, чем любое скачивание внутренней оценки. [S5]

**ПРОВЕРИТЬ:** privacy notice должен отдельно объяснять удаление из активной БД, истечение backups, пределы контроля над сохранением у провайдера и над копиями, уже экспортированными самим пользователем. Нельзя обещать удаление всех экземпляров во всех системах одним локальным запросом.

## 6. LLM Gateway и внешние поставщики

**ФАКТ БАЗОВОГО КОДА:** `research/feasibility/feasibility_spike.py` использует `/v1/responses` и `store=false`. Это настройка запроса, а не подтверждение Zero Data Retention аккаунта.

**ДОКУМЕНТАЦИЯ ПРОВАЙДЕРА:** OpenAI различает application state и abuse-monitoring logs. Последние могут включать prompts/responses; по умолчанию указан срок до 30 дней с исключениями. Специальные retention controls и региональные возможности имеют условия и ограничения endpoint/model/feature. [S10]

**ПРЕДЛОЖЕНИЕ:**

- Ключ доступен только backend; frontend, Git, логи и экспорт его не содержат. Для разных сред используются раздельные секреты и лимиты.
- Gateway убирает auth-данные, внутренние реквизиты аккаунта и обнаруженные ненужные идентификаторы до отправки; фильтр не считается гарантией распознавания любых персональных данных.
- Используется минимальный ролевой контекст, явный `store=false`, синхронные текстовые запросы и ограничение размера. Дополнительные tools/files/background features подключаются после проверки их данных и хранения.
- При переключении провайдера заново проверяются договор, регион, retention и качество. Ошибка API не разрешает скрыто направить диалог другому поставщику.
- В журнал попадают provider/model/version, latency, usage, код ошибки и request ID без тела запроса/ответа. Текст ошибки провайдера очищается перед логированием и выдачей пользователю.

**ПРОВЕРИТЬ ДО РЕАЛЬНЫХ ПОЛЬЗОВАТЕЛЕЙ:** настройки именно используемой организации и проекта; eligibility и фактическое включение retention controls; юридические условия; regional processing отдельно от storage; категории метаданных; subprocessors и механизм передачи. Сервер в Германии сам по себе не доказывает EU-only processing. Локальная история и состояние у провайдера — разные объекты удаления.

## 7. Защита приложения по этапам

**НОРМА:** Articles 25 и 32 требуют подходящих организационных и технических мер с учётом контекста и риска; privacy by default охватывает доступность и хранение. Наличие AI само по себе не заменяет анализ необходимости DPIA — оценки воздействия на защиту данных — по Article 35. [S6, S7]

### Level 1: доверенный локальный компьютер владельца

**ПРЕДЛОЖЕНИЕ:**

- FastAPI и UI доступны только через `127.0.0.1`/локальный loopback; PostgreSQL — через закрытую Docker-сеть или loopback. Порты не открываются наружу.
- Same-origin UI, строгий список допустимых Host/Origin, отсутствие wildcard CORS и CSRF-защита изменяющих запросов. Loopback не исключает обращений со злонамеренной страницы в том же браузере.
- Реплики выводятся как текст с экранированием; HTML/JavaScript из ввода и ответа модели не исполняется. Markdown, если появится, проходит ограниченный renderer.
- Ограничиваются длина сообщений, число ходов, размер запросов, стоимость и частота отправки. Повтор запроса не создаёт второй ход и второй результат.
- Секреты, БД, backups и raw-данные не входят в Git. Доступ к локальным файлам ограничен учётной записью владельца.

### До удалённого или совместного использования

**ПРЕДЛОЖЕНИЕ:** в дополнение к локальным мерам нужны проверяемый вход, серверные сессии, авторизация всех ресурсов, TLS, безопасные cookies (`HttpOnly`, `Secure`, выбранный `SameSite`), CSRF-проверка, истечение и отзыв сессий, лимиты на пользователя и безопасное восстановление доступа. Reverse proxy не публикует внутренний PostgreSQL. Ошибки не возвращают stack trace, скрытую карточку или детали чужого ресурса.

Администраторские действия ограничиваются необходимыми правами. Обновления зависимостей, резервное копирование и восстановление входят в эксплуатационный план. Владелец определяет контакт для инцидентов и порядок ограничения доступа, смены секретов и оценки последствий. Технические журналы не должны превращаться в запасную копию всех разговоров.

## 8. Уведомление пользователя и AI-прозрачность

**НОРМА:** Article 50(1)/(5) AI Act предусматривает информирование о прямом взаимодействии с AI; Article 50(2) отдельно касается машинно-читаемой маркировки генерируемых outputs. Комиссия указывает применение требований прозрачности с 2 августа 2026 года. [S8, S9]

**ПРЕДЛОЖЕНИЕ:** до первой реплики простым немецким языком сообщить, что клиент вымышленный и отвечает AI; объяснить назначение разбора и доступ к результатам. Правила хранения и контакт для запросов доступны рядом. Объяснения можно читать на родном языке; ключевые сведения должны быть понятны пользователю A2–B2.

Deterministic факт «найдено/не найдено» и AI-подсказки по качеству разговора обозначаются отдельно. Пользователь может сообщить об ошибке; система сохраняет происхождение оценки и её версию. Публикация результата или его передача тренеру не включается по умолчанию.

**ПРОВЕРИТЬ / ОТКРЫТО:** определить роль Klare KI как provider/deployer для конкретного способа выпуска и применимое техническое исполнение Article 50(2). Проверить возможности используемого поставщика и сохранность нужных metadata. Не считать произвольный внутренний флаг или видимую надпись доказательством полного исполнения нормы; конкретный стандарт и исключение здесь не утверждаются.

## 9. Проверки при реализации

Это критерии будущей приёмки, **не результаты тестов A01**. Проверки выполняются синтетическими данными; платные model tests для них не требуются.

| Проверка | PASS | FAIL |
|---|---|---|
| Граница локального запуска | Приложение и БД недоступны с внешнего интерфейса | Локальная конфигурация слушает публичный интерфейс без мер Level 2. |
| Скрытая карточка | До предусмотренного раскрытия отсутствует в UI payloads и неподходящих LLM-запросах | Скрытые facts уже переданы браузеру или Actor заранее. |
| Изоляция пользователей | Пользователь A не читает, не меняет, не экспортирует и не удаляет сессии B | Любой IDOR-доступ, в том числе через exports, progress или ошибки. |
| Роль тренера | Авторство сценария не открывает чужую историю | Автор-тренер получает общий список личных разговоров. |
| Отзыв передачи | Grant истёк/отозван — последующие чтения запрещены | Доступ остаётся через старую ссылку, cache или другой endpoint. |
| Удаление | Содержимое, связанные оценки и прогресс очищены; после restore остаются удалёнными | Данные возвращаются из backup, очереди или агрегата. |
| Retention | Границы каждого срока проверены; задача повторяема | Данные бессрочно остаются из-за пропуска запуска или ошибки. |
| Secrets и logs | Синтетические маркеры секрета/реплики отсутствуют в UI, логах, Git и exports | Содержимое появляется в диагностике или клиентском ответе. |
| XSS, Origin, CSRF | Вредоносная строка отображается текстом; чужой origin не меняет состояние | Исполнение HTML/JS или неавторизованное действие. |
| Provider configuration | Фактические условия и настройки записаны, обещания UI им соответствуют | Заявление ZDR/EU-only без подтверждения либо скрытый fallback. |

Перед открытием Level 2 заполнить краткий реестр обработки и выполнить DPIA screening с обоснованием результата. Расширение в учебные учреждения и оценку людей требует повторной проверки назначения. Это условие соответствующего релиза, а не требование остановить текущую документационную работу.
