# A01 — Модель данных и событий

**Статус:** предлагаемая схема, миграции не созданы. **Дата:** 2026-11-05. **База:** `2962a1b89cb8c9816decc8322ec92259993b3b03`. Согласование семантики результата и хранения — [OPEN_DECISIONS.md](OPEN_DECISIONS.md).

## 1. Правила модели

**Приоритетное уточнение A01.1:** [CONSULTATION_CORE.md](CONSULTATION_CORE.md) добавляет последовательные этапы потребностей/возможностей с резюме и проверенным подтверждением, отдельные состояния знания клиента и выяснения учеником, а также возможности поставщика. Исторические A/B/C остаются примером; их раскрытие не является достаточным учебным gate.

Сценарий, пользовательская тренировка и техническая попытка API — разные сущности. Каждая сессия закрепляет неизменяемые версии сценария, политики, rubric, Actor, Director и model profile. Отчёт воспроизводится по зафиксированным событиям, а не повторной генерацией разговора.

Неизменяемость здесь означает запрет незаметного редактирования принятой версии/события. Она не означает вечное хранение персональных данных: удаление пользователя, сессии и срок хранения имеют приоритет в соответствии с утверждённой политикой. Исторический исследовательский архив MISSION 00–02 отдельно сохраняется как синтетическое доказательство; его метрики не пересчитываются по новой схеме.

## 2. Сущности L1 и последующих уровней

| Сущность | Основные поля | Связи и правила |
|---|---|---|
| `users` | UUID, display_name optional, locale, feedback_language, created_at, status | L1 один локальный владелец без обязательного email. Источник role/ownership — сервер. Реальный account/auth — gate перед удалённым доступом. |
| `role_grants` | user_id, role, scope_id, granted_at | learner, scenario_author, operator; несколько ролей не дают автоматический доступ к чужой истории. В L1 роли владельца могут совпадать. |
| `scenarios` | id, slug, author_id, title, status, current_published_version | Корень карточки; архивирование скрывает её от нового выбора, не меняет текущие сессии. |
| `scenario_versions` | id, scenario_id, version, revision, schema_version, canonical_json, sha256, approval_by/time | JSON содержит public, private, atoms, disclosure rules, reply segments, rubric. Уникальны scenario_id+version. Published не редактируется. |
| `sessions` | id, owner_id, scenario_version_id, mode, status, version, completed_turns, reaction, authorized_fact_ids, emitted_atom_ids, version_bundle, expires_at | `mode=practice/preview`; preview не попадает в прогресс. State — материализованный итог событий, обновляется вместе с ними. |
| `turn_requests` | id, session_id, client_turn_id, payload_hash, expected_version, status, lease_token, lease_until, attempts_used, response_message_id, failure_phase, tentative_decision_optional | Уникальны session_id+client_turn_id. Содержит временный ввод до успешного хода; тот же ключ с другим текстом даёт конфликт. Tentative decision никогда не становится завершённым разрешением сама по себе. После terminal-status применяется удаление/срок хранения. |
| `messages` | id, session_id, turn_no, role, text, language, created_at, composer_manifest | Только зафиксированные сообщения; unique(session_id, turn_no, role). В manifest — IDs фрагментов и атомов, версия composer; клиент не может их задать. |
| `turn_events` | id, session_id, turn_no, event_type, question_message_id, answer_message_id, policy_version, evidence, state_before/after | События классификации/разрешения/выдачи/давления/ограничения системы. Цитаты содержат персональный текст и удаляются вместе с сессией. |
| `evaluations` | id, session_id, eval_version, rubric_version, core_result, technical_limitations_snapshot, feedback_status, feedback_language, created_at | Уникален session_id+eval_version. Core и AI-commentary отдельно. При finish снимаются ограничения незавершённых запросов, которые не дают credit/permission. Перегенерация советов не меняет count и прошлые версии без явного действия. |
| `model_profiles` | id, role, provider, model_id, parameters, prompt_version/hash, adapter_version, limits, approved_at | Нет API-ключа в таблице. Смена профиля применяется к новым сессиям; профили фиксируются в version_bundle. |
| `api_attempts` | request_id, turn_request_id/evaluation_id, role, profile_id, attempt_no, status, latency_ms, tokens, usage_known, reserved_cost, price_version | Содержимое prompts/responses по умолчанию не сохраняется. Неуспешная попытка не доказывает нулевую стоимость. |
| `deletion_jobs` | id, subject_scope, requested_at, state, completed_at, backup_cutoff | Удаляет производные/экспорт/доступ; минимальная suppression-запись предотвращает восстановление удалённых данных из backup. |
| `progress_snapshots` — L2 | owner_id, rubric_version, scenario_family, window, counts, sessions_included | Пересчитываемое представление; небольшие выборки и повтор знакомого кейса маркируются. Удаление исходной сессии пересчитывает данные. |
| `sharing_grants` — L3 | owner_id, recipient_id, session_id, allowed_fields, expires_at, revoked_at | Включается только отдельным решением ученика. Trainer role не заменяет grant; отзыв блокирует последующие обращения. |
| `organizations/memberships` — L3 | tenant_id, user_id, role, status | Изоляция на уровне запросов и ограничений; не добавлять фиктивный multi-tenant режим в L1. |

Таблицы — логический проект. Небольшие справочники можно реализовать конфигурацией; state/events нельзя прятать целиком в бесконтрольный JSON без схемы. PostgreSQL constraints обеспечивают уникальность/FK, а условия между несколькими строками реализуются в транзакции: [официальные ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).

## 3. Схема карточки сценария

| Блок | Что содержит | Кому виден |
|---|---|---|
| `identity` | id/version, title, sector, language level, author, status, learning objectives | Публичный безопасный поднабор. |
| `public_brief` | Только утверждённые обстоятельства, роль консультанта, первая реплика | Ученику и Actor; текст первой реплики проходит тот же content-review. |
| `private_facts` | Уникальные fact_id, атомы, значения, категория раскрытия | Policy и финальному Evaluation; author-editor. |
| `customer_knowledge` | Статус каждого существенного вопроса: known/undecided/does_not_know/refuses_to_disclose/not_applicable; отсутствие обязательного статуса блокирует публикацию | Policy/author; Actor только разрешённая для текущего ответа часть. |
| `supplier_capabilities` | Услуги, ограничения, условия/цены при их наличии, необходимые диагностика и полномочия, предпосылки действий | Ученику в необходимом объёме и Policy/Evaluation. |
| `consultation_requirements` | Критерии закрытия N/C, проверка резюме/подтверждения, допустимые неизвестности и итоговые действия | Policy/Evaluation; учебная инструкция без скрытых ответов доступна ученику. |
| `disclosure_rules` | Семантическая цель вопроса, положительные/отрицательные примеры, неоднозначность, `required_before_offer` по типу решения | Director получает критерий темы, без закрытого значения; Policy — полный контракт. |
| `persona` | Регистр Sie, длина фразы, стиль осторожности, допустимые реакции | Actor; описание поведения не должно подразумевать неизвестную биографию. |
| `response_segments` | id, текст DE, вариант, required_fact_ids, asserts_atom_ids, mood/topic/act, приоритет | Actor получает только допустимый subset; браузер видит только выбранный текст. |
| `rubric` | required_atoms, supporting_atoms, подсказки DE, правила found/partial/uncertain | Evaluation после завершения; не отправляется ученику заранее. |
| `acceptance` | Набор вопросов, review-флажки, версия проверок, подпись публикации | Author/QA; не часть prompts учащегося. |

Запрещены исполняемый Python, произвольные system-prompts, URL для загрузки и секреты в пользовательской карточке. Редактор создаёт данные в ограниченной схеме. Публикация проверяет ссылочную целостность atoms/segments, отсутствие утечек в public, достаточные варианты normal/guarded/unknown и тестовые примеры. Автоматическая валидация не доказывает семантическую корректность карточки; нужен review владельца.

## 4. Herr Krüger: сохранение источника и атомизация

Каноническая база исторического PoC — `PUBLIC` и `FACTS` в [feasibility_spike.py](../../research/feasibility/feasibility_spike.py). Иллюстрация PDF, стр. 3, не даёт задним числом разрешения на «вчера», маленькую печь, повторную поломку или симптомы нагрева. Новая карточка `krueger.v1` должна ссылаться на происхождение каждого добавленного факта и пройти новое утверждение. Legacy-карточка и её tests сохраняются.

| Группа | Возможные атомы | Предлагаемые обязательные атомы для результата |
|---|---|---|
| A | Предыдущий ремонт; весной; 1 200 €; результат неудачен; страх повторения | Неудачный опыт + страх повторения. Сезон/цена — поддерживающие детали, если владелец не утвердит иное. |
| B | Верхний предел; 8 000; EUR | Именно максимум 8 000 €, а не просто упоминание денег. |
| C | Совместное решение; жена; ведёт бухгалтерию | Совместное решение с женой. Бухгалтерия — поддерживающая деталь, если rubric не требует её отдельно. |

Это новая предлагаемая учебная семантика; она не заменяет старые A/B/C-эталоны и не превращает исторические ответы в новые PASS. Суммы фиксируются как числовые значения/валюта и проверенный отображаемый текст, а не вычисляются моделью.

## 5. Четыре уровня свидетельства

1. **Question qualified:** Director классифицировал конкретную реплику; есть исходный message_id и проверяемая цитата. Это модельное суждение, его истинность не обеспечивается одним JSON.
2. **Authorized:** Policy разрешила группе фактов участвовать в ответе, с причиной и версией правил.
3. **Emitted:** проверенная реплика клиента содержит определённые атомы; manifest связан с сохранённым answer_message_id. Это означает доступность текста ученику, не доказательство, что человек его прочитал/понял.
4. **Summary confirmed:** ученик корректно обобщил потребность, затем возможности/ограничения; подтверждение/исправление клиента проверено по свидетельствам. По уточнению владельца это обязательный gate L1, а не будущая функция. Он показывает корректность сформулированного понимания в данном упражнении; перенос навыка в реальные консультации отдельно не доказан.

Предлагаемый `found` = есть релевантный принятый вопрос + разрешение + все required_atoms группы включены в зафиксированные ответы текущей сессии. Атомы могут накопиться из нескольких завершённых ходов; каждый сохраняет собственный вопрос/ответ и происхождение. Поддерживающие атомы отображаются отдельно. Варианты результата: `found`, `partial`, `not_found`, `uncertain`, `system_limited`. Последние два не считаются неумением ученика.

Это канонический enum **на одну потребность**. `reason_codes` уточняют `not_asked`, `system_omission` и другие причины. Полнота всей оценки хранится отдельно как `complete`, `incomplete`, `not_assessable`; статус генерации AI-советов также отдельный (`pending`, `ready`, `unavailable`). Экран может показывать общую понятную подпись «Не удалось оценить», сохраняя различие причины в деталях.

Если правильный вопрос был задан, но ответ не пришёл/не содержит необходимого — показать «Вы спросили; ответ не дал достаточно информации», а не «Вы не спросили». Если фрагмент случайно раскрыт без разрешения, это системная ошибка, не достижение ученика; сессия не годится для сравнения прогресса.

## 6. Состояния и завершение

Операционный `session.status` ниже отделён от учебного `learning_phase`: `needs_discovery → capabilities_discovery → final_recommendation`. Сохраняются needs/constraints revisions, summaries, confirmation evidence и action preconditions. Существенное новое обстоятельство делает старое подтверждение неактуальным. Для каждого поля клиента есть состояние known/undecided/does_not_know/refuses_to_disclose/not_applicable, независимо от состояния выяснения учеником. Незаполненное обязательное поле автора — ошибка спецификации. Подробности и допустимые переходы — CONSULTATION_CORE.

Сессия: `active → finished`; отдельно `interrupted`, `deleted`. Возврат interrupted к active разрешён лишь до выдачи финального разбора и с прежней версией карточки. После finish скрытые ответы раскрыты; продолжение запрещено. Повтор создаёт новый session_id с отметкой repeat/exposure, не обнуляет знание человека.

Turn-request: `reserved → running → committed`; при техническом сбое `retryable_failed`, при нарушении ввода/лимита `terminal_failed`. Ограничение попыток общее для исходного client_turn_id; повторный клик не создаёт новый бюджет. Истёкший lease не даёт старому worker право commit после смены fencing-token.

Реакция L1: `neutral → guarded`, остаётся до конца сессии. Основание — подтверждённое давление или отдельный подтверждённый `premature_offer_detected`. В L1 нужен новый профиль `director-vnext`: он определяет наличие/тип конкретного предложения с проверяемым span текущей реплики; Policy проверяет подтверждение обоих учебных этапов в **предыдущем committed-state**, актуальность резюме и предпосылки действия. Вопрос и offer в одной реплике не делают предложение своевременным за счёт ещё не полученного ответа. Уточняющий вопрос о симптомах допустим при выяснении; предложение осмотра/выезда как следующего шага требует N/C, хотя оно не является обещанием ремонта. Эти новые сигналы проходят отдельную регрессию; legacy 74/74 их не подтверждает.

Неуверенный pressure/offer не создаёт подтверждённого негативного учебного события; ранее установленный guarded сохраняется. Это версионированное отличие от архивной Policy, которая меняла reaction по PRESSURE даже при confident=false. Давление не удаляет уже озвученные факты, не создаёт согласия на покупку и не запрещает все следующие содержательные вопросы. Возврат доверия после извинения остаётся будущей версией политики.

Обязательные ограничения: один pending turn на сессию; увеличение version ровно на успешный ход/завершение; no finish while pending; не более утверждённого лимита ученических ходов; posted text не редактируется; повторный finish возвращает существующий результат. Гонка delete/finish/commit разрешается проверкой статуса и version в транзакции.

## 7. Воспроизводимая оценка

`core_result` хранит для каждой группы её required/emitted atoms, статус, вопрос, ответ, объяснение missing/system-limit и версию rubric. Детерминированная пересборка на одном наборе committed-events даёт тот же core. Изменение модели не должно менять старый результат.

`feedback` хранится отдельно: язык, 2–3 рекомендации, source_message_ids, точные цитаты, немецкая альтернативная формулировка, reviewer/status и profile_version. Неподтверждённые цитаты отклоняются. Если генерация советов не удалась, core и утверждённые сценарные примеры доступны; UI сообщает, что дополнительный AI-разбор недоступен. В L1 нет единого «87/100», CEFR-сертификата, прогноза продаж или ранжирования людей.

### Неполученный ответ как ограничение оценки

При finish Evaluation получает также неизменяемый `technical_limitations_snapshot` из окончательно не завершённых/отменённых `turn_requests`: request_id, фазу/причину сбоя, время и при необходимости исходный текст вопроса с тем же сроком хранения, что transcript. Допустим отдельно помеченный валидированный tentative Director-result. Этот снимок **не** создаёт messages, авторизации или Finding. Успешно восстановленный затем запрос не считается непреодолённым ограничением.

Так разбор знает о вопросе, не дошедшем до semantic commit. Если Director его не обработал, текст объяснения — «Этот вопрос не удалось обработать», без утверждения о правильности. Если Director распознал B, но Actor не ответил, — «Вопрос распознан как вопрос о бюджете, но ответ клиента не получен». Для находок источником остаются только committed-events. Неопределённость классификации и техническое ограничение имеют разные reason_codes.

## 8. Хранение, удаление и перенос

Конкретные проектные сроки и правовые основания собраны в [SECURITY_AND_GDPR.md](SECURITY_AND_GDPR.md); числа не являются установленными законом сроками. Удаление сессии каскадно убирает messages, events, feedback, ссылочный progress, pending input, sharing и exports. Минимальные content-free usage-счётчики не должны сохранять обратную связь с учеником без отдельной необходимости и срока.

Полное удаление сессии пользователем отличается от автоматического истечения срока **подробного содержимого**. Предложение 30/90 дней означает: после 30 дней удаляются transcript, цитаты, подробные events/feedback; при включённом личном прогрессе отдельно могут оставаться до 90 дней минимальные outcome counts, версии rubric/scenario и признак repeat, без текста. Полный разбор после этого недоступен. Это отдельная цель/настройка хранения. Явное удаление сессии или аккаунта убирает и такой вклад; если владелец не принимает раздельное хранение, всё очищается через 30 дней.

Backups зашифрованы и ограничены сроком; restore сначала применяет актуальный журнал удалений. Псевдонимизация user_id не равна анонимизации текста. API-ключи находятся в окружении/secret store вне базы и репозитория. Дамп БД и реальные сообщения не становятся Git-тестовыми fixtures.

Миграции последовательные с отдельной проверкой upgrade/restore. Новая версия карточки не переписывает JSON действующих сессий; удаление старого опубликованного контента возможно только с учётом зависимостей и приватности. Личная история и коммерческие отчёты вводятся после принятия этих правил, а не заменяют их.
