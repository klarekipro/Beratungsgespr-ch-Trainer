# A01 — Решения владельца перед разработкой

**Статус: AWAITING OWNER DECISION.** Дата: 2026-11-05. База: `2962a1b89cb8c9816decc8322ec92259993b3b03`.

Документы A01 являются конкретным проектным предложением. Публикация документации не означает утверждения Dashboard, платного бюджета, реализации или deployment. Владелец обсуждает и фиксирует решения, после чего начинается отдельная инженерная миссия.

## 1. Рекомендуемый комплект решений для первого обсуждения

Предлагается минимальный Dashboard, локальная личная версия, три клиента и простой редактор, контролируемый Actor, разбор DE/RU и 15 ходов ученика. Это цельный вариант L1, а не уже принятое решение. Главный компромисс — проверить, достаточно ли естественна речь из утверждённых вариантов. Полный список ниже позволяет изменить любой пункт, не потеряв зависимости.

## 2. Какие решения уже заданы исходными материалами

Тема — Beratungsgespräch-Trainer; разговор на немецком; контролируемые скрытые потребности; разбор с конкретными вопросами; личные результаты ученика; отсутствие работодателя как оценщика. A01 выполняет анализ/документацию, не production-код, не платные тесты, не новые облачные ресурсы и не изменение инфраструктуры. Эти границы не предлагается заново утверждать.

Историческая статистика сохраняется: 46/54 → 74/74 Director; CONDITIONAL PASS PoC; Actor Grounding OPEN; MISSION 02 FAIL по приёмке / BLOCKED по выполнению. Новый проектный документ не является основанием изменить эти статусы.

## 3. Что может решить исполнитель без новой продуктовой дискуссии

После принятия соответствующего scope исполнитель выбирает организацию внутренних функций, совместимые закреплённые версии библиотек, имена миграций, базовые CSS детали в рамках согласованной навигации, способы параметризованных SQL-запросов и структуру технических логов. Эти решения не должны изменять источники фактов, правила оценки, цену без лимита, доступ к данным или пользовательский scope.

## 4. Форма фиксации

Для каждой изменяемой строки записываются выбранный вариант, дата, ответственный, последствия для scope/тестов/срока. Например: `D01 = minimal; D02 = 3 clients + editor; D03 = controlled candidate; D04 = proposed core atoms; D05 = 15 learner turns`. Это пример формата, **не запись принятого решения**.

Если владелец отвергает управляемый Actor, следующий шаг — конкретная миссия полной приёмки свободного v2/нового prompt с сохранением старого FAIL/BLOCKED до новых доказательств. Если выбирает стандартный Dashboard или remote-L1, план получает дополнительный объём явно. Если сроки требуют одного клиента, выпуск маркируется изменённой scope-version, а остальные требования PDF остаются в backlog, не исчезают.

Успех 40-вызовной проверки v2 подтверждает только её проверенный scope grounding/роли. Для доказательного Evaluation свободного текста дополнительно нужен контракт извлечения атомов с цитатами и возможным `uncertain` либо ручная верификация. Его приёмка и стоимость не включаются автоматически в восьмидневный план управляемого варианта.

## 5. Точка остановки

Первое обсуждение посвящено **D01–D05**: что пользователь видит, полный ли это исходный MVP, какой компромисс Actor принимает владелец, как показывается результат и каков лимит тренировки. D06–D13 уточняют выполнимый план. Разработка начинается только отдельным поручением после этого обсуждения.
