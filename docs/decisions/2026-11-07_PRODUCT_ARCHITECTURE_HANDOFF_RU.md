## 2. Неподвижные продуктовые принципы

1. Продукт — практический тренажёр консультационных разговоров, а не список формальных вопросов/ответов.
2. Обучающая дисциплина: **(1) потребности → (2) возможности и ограничения → (3) обоснованный итоговый шаг/предложение**. Не допускать успешного учебного результата при преждевременном предложении без выяснения критичных данных.
3. Первоначальная потребность может быть произнесена самим клиентом. Не требовать от ученика спрашивать «зачем вы пришли?» повторно. Оценивать **полноту достаточных сведений**, а не количество вопросов.
4. Коммерческий результат и качество консультации — разные измерения. Предварительное согласие на диагностику не равно заказу ремонта; непроставленная оценка наставника не равна провалу.
5. Технические тесты Codex — минимальная проверка функциональности, безопасности и сохранности. Человеческий качественный разбор реальных диалогов — обязательный критерий поведения AI; количество прошедших unit-тестов само по себе не доказывает полезность.
6. На этапе WBS **не менять OpenAI Simple Actor на Convai, Letta или другой engine**. Альтернативные движки возвращаются в исследование только при неудовлетворительном результате текущей архитектуры.

## 3. Подтверждённая продуктовая структура (по отчётам A10–A13)

- Один Python/FastAPI backend, SQLite, OpenAI Responses API / Simple Actor, один локальный запуск.
- Два независимых кабинета: Mentor/Admin и Employee/Learner, собственные логины/пароли, история сотрудника и разграничение API.
- Интерфейсы DE/EN/RU, немецкий как default. Язык интерфейса **не** задаёт автоматически язык консультации.
- Persona Studio с версионируемыми профилями; изменения применяются **только к новым тренировкам**, предыдущие сессии сохраняют снимок.
- Три учебных сценария × два целевых характера: решительный и нерешительный.
- Диктовка → транскрипция → редактируемый текст → **явная** отправка; не полноценный realtime voice-to-voice.
- После A13 Mentor может сохранять отметки этапов, коммерческий исход, соответствие возможностям компании и комментарий. До оценки показывать «Ожидает оценки наставника», не автоматический FAIL.

## 4. Контракт данных: НЕ смешивать шесть сущностей

### 4.1 Base Persona — кто этот человек

Постоянные настройки: психологический тип, характер, стиль речи, отношение к продавцу, сомнения, манера задавать вопросы, принятие решений, реакция на давление, повторения, типичные выражения. Это **поведение**, не источник технических фактов, сумм или истории ремонта.

### 4.2 Scenario — что действительно произошло

Открытая постановка, факты, неизвестности, потенциально скрытые сведения, условия раскрытия, допустимые исходы. Незаполненное поле **не** разрешает AI выдумывать значение: необходимо различать `unknown-to-customer`, `not-specified-by-author`, `known-but-not-yet-disclosed`, `disclosed`.

### 4.3 Session Modifiers — какие условия действуют сегодня

Настроение, срочность, предыдущий разговор, сравнение конкурентов, уровень доверия. В версии для WBS можно оставить как схему/будущие настройки без сложной реализации.

### 4.4 Company Profile — что действительно может продавец

Структурированные услуги, ограничения, цены, условия, компетенции. Источник фактов о компании для правил и последующей оценки, **не скрытая внутренняя карточка в промпте клиента**. Не позволять Actor перенимать роль сервисной компании.

### 4.5 Training Mode — что именно тренируем

**Будущая независимая настройка:** `consultative_sales` (базовая), `technical_knowledge`, `company_procedure`. Не путать с типом характера и сложностью. Дотошный технический клиент уместен в техническом режиме, но не обязан быть базовой моделью «решительного».

### 4.6 Evaluation Policy — по чему оцениваем

Разделять: (a) учебные этапы, (b) коммерческий исход, (c) соответствие компании, (d) знания/процедуры для будущих режимов. Проверка должна ссылаться на конкретные реплики/правила, а не считать число вопросов. Оценка наставника — текущая действующая опора; не утверждать автоматический экзаменатор без реализации.

## 5. Архитектурное направление (не новый scope для WBS)

`Mentor Persona/Scenario/Company → Python controller (versions/permissions/history) → OpenAI Actor (restricted client context) → transcript → Mentor review`.

При будущей проверке технических знаний предусмотреть отдельную корпоративную базу знаний: (1) структурированные правила с обязательной силой; (2) документы и процедуры для поискового извлечения фрагментов, когда объём действительно требует RAG. **Evaluator** после беседы использует утверждённую Company KB; **Actor** не получает внутреннюю полноту регламентов. Отдельный режим знаний требует собственных критериев; не навешивать его незаметно на продажи.

Будущая многокомпанейская версия: изоляция tenancy, доступов, версий документов, DPA/DSGVO и правил контроля сотрудников. Не деплоить на VPS до отдельной оценки доступа/HTTPS/секретов и данных.

- Владелец умышленно пропускал уточнение типа печи и точного времени, проверяя качество реакции. Правильная оценка различает **обязательные данные совместимости** и **детали, которые допустимо подтвердить позже**.
