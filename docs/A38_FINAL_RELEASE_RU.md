### Recovery — инструкция, не выполненный откат

Восстановление данных может потерять изменения после snapshot, поэтому требует отдельного решения владельца. A38 не выполняет restore drill поверх production.

1. Проверить выбранную дату/комплект и SHA-256 (`shasum -a 256`), integrity/FK read-only. Сделать свежий SQLite backup текущего состояния перед любым возвратом; текущие новые данные не удалять.
2. Штатно остановить только принадлежащий установке процесс: `.venv/bin/python scripts/local_installation.py stop`. Сохранить целиком текущий runtime/dashboard с WAL/SHM и diagnostic files в отдельную приватную папку; не удалять и не смешивать sidecars разных баз.
3. Через SQLite backup API из выбранного проверенного backup создать **новую** trainer.sqlite3 в staging directory. Проверить integrity/FK/company version/исторические снимки и issued PDF snapshots. Не запускать тестовые conversations/issue на рабочей копии.
4. Только после отдельного разрешения владельца переключить runtime/dashboard на подготовленную копию, права0700/0600, сохранив прежнюю папку. Старые WAL/SHM не переносить к восстановленному файлу. Не использовать безусловно launcher update/rollback, который способен сменить checkout/данные.
5. Штатный start, read-only status/правильный DB path и проверка уже сохранённых документов. Работающий код должен соответствовать данным A37. Откат к A35 SQLite поверх текущих результатов запрещён без отдельного согласованного возврата данных.

Для локального source recovery — source.bundle/проверенный private GitHub commit; вернуть исходники в отдельную папку/ветку, не hard-reset поверх пользовательских изменений. Code rollback не означает DB rollback. Полное восстановление на другой машине ещё не проверено.
